# 프론트 웹 페이지 구현 가이드라인

> 목적: `Usecase_scenario.md`를 실제 웹 화면으로 옮길 때 공통으로 따라야 할 화면 구성, 라우팅, 상태 관리, API 연동 기준을 정리한다.
> 기준 문서: `Usecase_scenario.md`, `WebsiteConceptGapReview.md`, `FrontendIntegrationReview.md`, `ApiSpec.md`
> 원칙: 이 문서는 프론트 구현 기준이다. 백엔드 API 추가/변경 필요 사항은 `FrontendApiGap.md`에 별도로 정리한다.

## 1. 전체 방향

이 프로젝트의 웹은 단일 홍보용 웹사이트가 아니라 **보험 업무 운영 포털 + 고객 셀프서비스 포털**이다.

따라서 첫 화면과 메뉴는 마케팅 페이지보다 업무 처리에 집중한다.

- 직원은 목록, 필터, 상세 패널, 승인/반려/실행 같은 action을 빠르게 처리해야 한다.
- 고객은 본인 계약, 납입, 해지, 사고 접수, 보험금 청구, 문의 같은 셀프서비스 흐름을 이해하기 쉬워야 한다.
- 알림, 토스트, 화면 이동, 버튼 노출, 업무 단계 시각화는 프론트 책임으로 둔다.
- 백엔드는 상태값, 업무번호, 날짜, 검증 결과, 파일 URL 같은 안정적인 데이터를 제공해야 한다.

  - 보험금 산출

### 2.2 고객 포털

고객 포털은 Phase 3 이후 범위로 보는 것이 현실적이다.

주요 메뉴:

- 보험상품 조회/신청

- 보험료 납입
- 보험 해지 신청
- 사고 접수
- 보험금 청구

고객 포털은 직원 포털보다 단계를 더 명확하게 나눈다. 예를 들어 보험금 청구는 약관 동의, 본인 인증, 기본 정보 확인, 청구 내용 입력, 계좌 입력, 서류 첨부, 최종 확인 순서의 wizard 화면이 적합하다.

## 3. 화면 패턴

### 3.1 업무 목록 화면

대부분의 직원 화면은 다음 구조를 기본으로 한다.

- 상단: 조회 조건 영역
- 본문: 테이블
- 우측 또는 모달: 상세 패널
- 하단: 페이지네이션
- 상단 우측: 신규 등록 또는 주요 action

적용 화면:

- 계약 조회
- 청구 목록
- 채널 심사
- 영업조직 평가
- 영업활동 관리
- 교육 계획
- 문의 목록
- 납부 내역 관리
- 환급 지급

기본 동작:

- 초기 진입 시 업무상 가장 자연스러운 기본 필터를 적용한다.
- 행 클릭 시 상세 패널을 연다.
- 상세 패널에서 상태별 action 버튼을 노출한다.
- action 성공 후 목록을 다시 조회한다.
- 빈 결과는 에러가 아니라 empty state로 표시한다.

### 3.2 상세 패널

상세 패널은 목록 컨텍스트를 유지하면서 한 건을 처리하기 위한 UI다.

포함 요소:

- 업무번호
- 고객/채널/계약 등 식별 정보
- 현재 상태
- 핵심 수치
- 등록일/처리일
- 상태별 action 버튼

상세 패널에서 action이 많아지면 독립 페이지보다 하위 모달을 우선 사용한다.

예:

- 채널 심사: 승인/거절
- 영업조직 평가: 성과급 요청
- 교육 계획: 승인/반려
- 문의 상세: 답변 등록
- 청구 상세: 조사/산출/지급 단계 이동

### 3.3 등록/수정 폼

등록/수정 화면은 유스케이스의 필수 항목을 기준으로 만든다.

공통 기준:

- 필수 항목은 label 또는 helper text로 명확히 표시한다.
- 저장 버튼 클릭 전 클라이언트 검증을 수행한다.
- 서버 validation 실패는 `fieldErrors`를 각 필드 하단에 매핑한다.
- 취소 시 작성 중인 값이 있으면 확인 팝업을 띄운다.
- 저장 성공 후 생성된 업무번호, 등록일시, 대상 식별자를 보여준다.

### 3.4 Workflow/Wizard 화면

고객 포털이나 복잡한 업무는 단계형 화면이 적합하다.

적용 화면:

- 보험료 납입
- 보험금 청구
- 사고 접수
- 보험 신청
- 부활 신청
- 보험 해지

기본 기준:

- 각 단계의 입력값은 다음 단계로 넘어가기 전에 검증한다.
- 최종 제출 전 요약 화면을 제공한다.
- 중간 취소 시 작성 내용 삭제 확인 팝업을 제공한다.
- 새로고침 복원이 필요한 workflow는 서버 저장 API 또는 임시저장 정책이 필요하다.

## 4. 상태와 버튼 노출

현재 결정은 `canApprove`, `nextAction` 같은 화면 전용 파생 필드를 백엔드가 필수로 내려주지 않는 것이다.

따라서 프론트는 상태값을 기준으로 버튼을 노출한다.

예:

- 채널 심사 `PENDING`: 승인, 거절 버튼 노출
- 문의 `ANSWERED`: 답변 등록 버튼 숨김
- 교육 계획 `DRAFT`: 승인 요청 가능
- 교육 계획 `PENDING`: 승인/반려 가능
- 청구 산출 `APPROVED`: 지급 생성 가능

주의할 점:

- 프론트 버튼 숨김은 사용자 경험을 위한 것이다.
- 실제 업무 규칙은 백엔드에서도 검증해야 한다.
- 상태 전이 표는 별도 문서 또는 `ApiSpec.md`에 누적한다.

## 5. API 연동 기준

### 5.1 인증

- 로그인 이후 API 요청은 세션 쿠키 기반이다.
- axios는 `withCredentials: true`를 사용한다.
- fetch를 쓰는 경우 `credentials: "include"`를 사용한다.
- 401 응답이면 로그인 페이지로 이동한다.
- 비밀번호 변경이 필요한 계정은 업무 화면 접근 전에 비밀번호 변경 화면으로 유도한다.

### 5.2 목록 응답

테이블 화면은 가능하면 다음 형태를 기준으로 한다.

```json
{
  "page": 0,
  "size": 20,
  "total": 0,
  "items": []
}
```

배열을 직접 반환하는 기존 API는 화면별 adapter를 두어 공통 테이블이 깨지지 않게 처리한다.

### 5.3 에러 응답

공통 에러 응답은 다음 필드를 우선 사용한다.

- `status`: HTTP status
- `code`: 프론트 분기용 안정 코드
- `message`: 사용자에게 보여줄 수 있는 메시지
- `path`: 요청 path
- `fieldErrors`: 필드 검증 오류

화면 처리 기준:

- 400: 사용자가 수정할 수 있는 입력 오류
- 401: 로그인 필요
- 403: 권한 없음
- 404: 목록으로 돌아갈 수 있는 리소스 없음
- 409: 상태 전이 충돌 또는 중복 처리
- 500: 재시도 안내

### 5.4 Enum/Option

현재는 option API를 만들지 않고 `ApiSpec.md`를 기준으로 프론트 상수를 정의한다.

프론트에서는 다음 구조를 권장한다.

```js
export const CHANNEL_TYPES = [
  { value: 'AGENT', label: '설계사' },
  { value: 'AGENCY', label: '대리점' },
];
```

서버 enum 이름과 화면 label을 분리해야 한다. 화면 label을 API request 값으로 직접 보내면 변경에 취약해진다.

## 6. 컴포넌트 기준

### 6.1 공통 컴포넌트 후보

- `DataTable`
- `SearchFilters`
- `DetailPanel`
- `FormModal`
- `ConfirmDialog`
- `StatusBadge`
- `Pagination`
- `EmptyState`
- `ErrorState`
- `LoadingState`

현재 코드에는 `Pagination`, `StatusBadge`, layout 컴포넌트가 있다. 새 화면은 기존 패턴을 우선 재사용한다.

### 6.2 상태 관리

목록과 상세 패널은 보통 같은 페이지 컴포넌트에서 상태를 공유한다.

예:

- `selectedItem`
- `filters`
- `page`
- `isDetailOpen`
- `isSubmitting`

여러 형제 컴포넌트가 같은 값을 필요로 하면 가까운 공통 부모로 state를 끌어올린다. React 공식 문서의 "컴포넌트 간 State 공유하기"가 이 패턴을 설명한다.

참고:

- https://ko.react.dev/learn/sharing-state-between-components

서버 상태는 이후 React Query 같은 라이브러리를 도입하면 더 안정적으로 관리할 수 있다. 다만 현재 단계에서는 axios API 모듈과 페이지 단위 `useEffect`로도 MVP 구현은 가능하다.

## 7. 구현 우선순위

### Phase 1: 내부 직원용 탐색 MVP

목표: 로그인 후 주요 업무 목록을 API로 조회하고 상세를 볼 수 있다.

- 계약 목록/상세
- 청구 목록/상세
- 영업활동 목록
- 채널 심사
- 영업조직 평가
- 교육 계획
- 문의 목록

### Phase 2: 업무 workflow MVP

목표: 상세 화면에서 실제 상태 전이 action을 수행한다.

- 채널 심사 승인/거절
- 영업조직 평가 등록/성과급 요청
- 교육 계획 승인/반려/제반/실행
- 청구 조사/산출/지급
- 납입 preview/submit/확정
- 문의 답변

### Phase 3: 고객 포털

목표: 고객이 본인 업무를 직접 신청/조회한다.

- 상담 신청
- 내 계약 조회
- 보험료 납입
- 보험 해지
- 사고 접수
- 보험금 청구
- 문의 등록/내역

### Phase 4: 운영 완성도

목표: 유스케이스의 운영 요구를 보강한다.

- 파일/S3
- 통계/그래프
- 엑셀 다운로드
- 알림 이력
- audit/logging
- 직원 세부 권한

## 8. 화면 설계 체크리스트

새 화면을 만들기 전에 아래 항목을 확인한다.

- 유스케이스에서 actor가 누구인가?
- 목록 조회가 필요한가?
- 상세 조회가 필요한가?
- 생성/수정/삭제/취소가 필요한가?
- 승인/반려/확정/실행 같은 상태 전이가 있는가?
- 성공 후 보여줄 완료 정보는 무엇인가?
- 취소 시 작성 중 데이터 경고가 필요한가?
- 빈 결과 메시지가 정의되어 있는가?
- 서버 validation 오류를 필드에 표시할 수 있는가?
- 새로고침 후 화면 복원이 가능한가?
- 파일 업로드/다운로드가 필요한가?
- 고객 본인 데이터만 보여줘야 하는가?
- 현재 API로 가능한가, 추가 API가 필요한가?

# Kindred Assurance 디자인 가이드라인 (Standard v2)

## 1. 개요

본 가이드라인은 Kindred Assurance 보험 시스템의 일관된 사용자 경험(UX)과 시각적 아이덴티티(UI)를 보장하기 위해 작성되었습니다.

## 2. 디자인 원칙

- **Clean & Professional**: 불필요한 장식을 배제하고 #f7f9fb 단색 배경을 사용하여 콘텐츠 가독성을 극대화합니다.
- **Friendly Touch**: 딱딱한 기업용 시스템의 느낌을 완화하기 위해 부드러운 클레이 스타일의 3D 이모지를 핵심 섹션에 활용합니다.
- **Consistency**: 모든 내부 운영 페이지는 동일한 네비게이션 구조를 공유합니다.

## 3. 주요 구성 요소

### 3.1. 레이아웃 (Layout)

- **외부 포털**: 상단바(TopNavBar) + 메인 콘텐츠 영역. 사이드바 없음.
- **내부 관리 시스템**: 상단바(TopNavBar) + 접이식 사이드바(Collapsible SideNavBar) + 메인 콘텐츠 영역.

### 3.2. 컬러 시스템 (Color Palette)

- **Primary**: Emerald Green (#10b981) - 버튼, 활성 상태, 강조 포인트.
- **Background**: Solid Light Gray (#f7f9fb) - 모든 화면의 기본 배경.
- **Surface**: White (#ffffff) - 카드, 패널 등 콘텐츠 컨테이너.

### 3.3. 네비게이션 (Navigation)

- **SideNavBar**: 좌측 고정. 접기/펼치기 기능을 통해 업무 영역을 최적화할 수 있어야 합니다.
- **TopNavBar**: 시스템 전체 공통 적용.

### 3.4. 아이콘 및 그래픽 (Visual Assets)

- **3D Emojis**: 투명 배경의 3D 클레이 스타일 이모지만 사용합니다.
- **Status Badges**: 원형 모서리가 적용된 부드러운 색상의 배지를 사용합니다.

## 4. 타이포그래피 (Typography)

- **Font Family**: Inter (Sans-serif)
- **Hierarchy**: Headlines(Bold), Labels(Medium), Body(Regular)의 명확한 구분.
